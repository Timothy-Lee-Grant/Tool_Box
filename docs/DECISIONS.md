# Architecture Decision Records

Append-only. Each record: context → decision → consequences. Reversing a decision gets a new ADR that supersedes the old one, never an edit.

---

## ADR-001 — C# with the official ModelContextProtocol SDK (2026-07-16)

**Context:** Primary future client is LLM_Monitor (Python), but MCP is a language-neutral protocol; server language is independent of client language. Career target is .NET backend roles.
**Decision:** C#/.NET, using the official `ModelContextProtocol` NuGet package. Never hand-roll the JSON-RPC layer.
**Consequences:** Attribute-based tool registration, hosting/DI integration, stdio + HTTP transports for free. Python agents consume the server via `langchain-mcp-adapters`.

## ADR-002 — stdio transport first, HTTP later (2026-07-16)

**Context:** Simplest viable product wins; HTTP adds networking, auth, and container concerns to plan 001.
**Decision:** MVP speaks stdio only. Streamable HTTP (for LLM_Monitor's compose network) is plan 002.
**Consequences:** Architecture must keep transports swappable — hence ADR-003's boundary: only the Host knows the transport.

## ADR-003 — Host / Core / Toolsets project layout (2026-07-16)

**Context:** The platform will grow many toolsets; domain logic and protocol plumbing must not tangle.
**Decision:** Thin Host (composition root only), Core (shared plumbing, no MCP hosting deps), one project per toolset. Separate early, abstract late: no dynamic plugin loader until two real toolsets exist (plan 003).
**Consequences:** A toolset costs the Host one composition line. Tools are testable as plain methods with no server running.

## ADR-004 — stderr-only logging (2026-07-16)

**Context:** In a stdio MCP server, stdout is the JSON-RPC wire. Anything else written there corrupts the protocol, and the failure surfaces as a baffling parse error on the *client*.
**Decision:** `UseStderrOnly()` clears providers and pins console logging to stderr; it is the first line of Host configuration so nothing can register ahead of it.
**Consequences:** Verified by the stdout purity test: `dotnet run --project src/ToolBox.Host 2>/dev/null` must print nothing.

## ADR-005 — Toolsets register via IMcpServerBuilder extensions (2026-07-16)

**Context:** Step 2.4 originally sketched `IServiceCollection` extensions, but tool registration (`WithTools<T>()`) lives on `IMcpServerBuilder`.
**Decision:** Each toolset exposes exactly one public doorway: `Add<Name>Toolset(this IMcpServerBuilder)`, which registers its `ToolsetDescriptor` and its tool types.
**Consequences:** Host composition reads as a fluent list of capabilities and contains zero tool-type names. Toolsets reference the MCP package for attributes, but the *transport* choice remains exclusively the Host's.

## ADR-006 — Target net10.0 (current LTS) (2026-07-16)

**Context:** Scaffolding defaulted to net11.0 because a .NET 11 *preview* SDK was installed. Lesson learned during Step 3: an SDK can compile a target it cannot run — executing net10.0 binaries requires the net10.0 runtime to be installed separately.
**Decision:** Target `net10.0` (LTS, supported to Nov 2028), pinned once in `Directory.Build.props`. Projects must not set their own TFM (csproj values silently override the props file).
**Consequences:** Stable base until 2028; CI pins `dotnet-version: 10.0.x` to match.

## ADR-007 — Single binary, dual transport (2026-07-16)

**Context:** Plan 002 adds streamable HTTP for containerized/remote consumers (LLM_Monitor) while stdio remains the local-client transport. A second Host project was considered.
**Decision:** One `ToolBox.Host` binary; transport selected at startup with precedence `--transport` flag > `TOOLBOX_TRANSPORT` env > `appsettings.json` (default stdio). Shared composition lives in `AddToolBoxServer()`; each path attaches only its wire. HTTP mode runs stateless (SDK recommendation: no session affinity, simpler clients).
**Consequences:** Toolsets/Core needed zero changes to gain a transport (measured: zero diffs in plan 002). The same binary can later run on a Raspberry Pi with a different toolset roster — deployment identity is configuration, not compilation. Cost: the Host carries ASP.NET Core via FrameworkReference even in stdio mode (accepted; shared framework, not published weight per-mode).

## ADR-008 — HTTP security posture v1: unauthenticated, network-isolated (2026-07-16)

**Context:** The HTTP endpoint executes tools on behalf of anyone who can reach it. v1 has no authentication.
**Decision:** Isolation is the control, and it's layered: (1) inside consuming composes (LLM_Monitor) the service publishes **no ports** — reachable only on the internal network, and exposure is a conscious config change (the lockdown-is-a-config-change pattern); (2) Tool_Box's own dev compose publishes `8081:8080` because that file *is* the dev environment; (3) `AllowedHosts` is pinned to loopback + the compose service name per SDK guidance (DNS-rebinding defense — Kestrel doesn't validate Host headers by default); (4) all current tools are read-only.
**Consequences:** Never deploy this endpoint beyond a trusted network segment. Authentication (HTTP auth on the transport) is scheduled for whenever the first non-trusted network appears — and must land *before* any write-classified toolset ships over HTTP. **Superseded in part by ADR-011** (2026-07-21): item (4) turned out to be a promise this project didn't keep literally — read below.

## ADR-009 — Voxel world state: a single global singleton (2026-07-21)

**Context:** Plan 003 is the platform's first stateful toolset. A `VoxelWorld` must persist across tool calls within a session. The "correct" multi-tenant answer would be state scoped per MCP session (the SDK supports per-connection server instances over streamable HTTP), but no real multi-client scenario has been observed yet.
**Decision:** One process-wide singleton `VoxelWorld`, registered the same way `ServerInfoProvider` is — plain `Dictionary`-backed, no locking, no persistence. A reference implementation this toolset is modeled on (a working voxel-builder MCP server) uses the identical pattern for the identical reason: one client, one process, nothing to protect against. Session-scoped state is explicitly deferred until a real multi-client demo needs it — "abstract from evidence, not imagination," the same principle ADR-003 applied to the plugin loader.
**Consequences:** Two simultaneous HTTP-connected agents would edit the same world — a known, accepted v1 limitation, not an oversight. `world.Clear()` affects every connected viewer/client at once. Revisit if/when a genuine multi-client use case appears.

## ADR-010 — Toolsets may register companion `IHostedService`s (2026-07-21)

**Context:** The Voxel toolset needs a live browser viewer, which needs a WebSocket broadcast running continuously — but that has nothing to do with the MCP transport itself, and must work identically whether the Host is running stdio or HTTP (ADR-007's transport independence shouldn't have exceptions for one toolset's demo feature).
**Decision:** Generalizes ADR-005 one step further: a toolset's `Add<Name>Toolset()` extension may register not just tools, but its own `BackgroundService` (`VoxelViewerBroadcastService`), via the ordinary `services.AddHostedService<T>()`. This works unmodified under both Host composition paths (`Host.CreateApplicationBuilder` for stdio, `WebApplication.CreateBuilder` for HTTP) because both ultimately build on the same `Microsoft.Extensions.Hosting` `IHost` — proven directly, not assumed, by booting both shapes with a real WebSocket client attached during plan 003 Step 4.
**Consequences:** A new pattern precedent for future visual/interactive toolsets (a future scene-composer toolset, for example, could reuse this rather than re-deriving it). The companion service binds its own port range (8090-8093 for Voxel), independent of and never colliding with whatever port the MCP HTTP transport itself uses (8080) — verified directly, both running in the same process simultaneously.

## ADR-011 — Supersedes ADR-008 item (4): isolation, not tool classification, was always the real control (2026-07-21)

**Context:** ADR-008 listed "all current tools are read-only" as one of four mitigating factors for the unauthenticated HTTP posture, and its consequences line said authentication "must land before any write-classified toolset ships over HTTP." Plan 003's Voxel toolset is the first write-classified toolset (`place_*`, `remove_box`, `mirror`, `clear` all mutate), and plan 003 explicitly deferred HTTP authentication to a future plan — so shipping Voxel over HTTP now means literally doing the thing ADR-008 said shouldn't happen yet. This was surfaced explicitly to Timothy (plan 003, Stage 3 Step 7.3) rather than silently decided.
**Decision:** Ship Voxel over both transports, preserving ADR-007's "identical toolset roster regardless of transport" invariant. Re-examining ADR-008's own four items: (1)-(3) — no published ports outside a trusted network, dev-only port mapping, `AllowedHosts` pinned against DNS rebinding — are deployment-topology controls that apply equally to read and write tools; they were always the *actual* protection. Item (4) ("all current tools are read-only") was true by coincidence of what had been built so far, not a designed-in gate, and treating it as a hard precondition for every future toolset would mean no write toolset could *ever* ship over HTTP without a full auth implementation first — a much larger bar than this project's staged, evidence-driven process has applied anywhere else.
**Consequences:** Authentication is still real future work, scheduled for "whenever the first non-trusted network appears" exactly as ADR-008 said — that part stands. What's retired is treating tool read/write classification as itself a gating condition. The operative rule going forward: **never publish the HTTP transport's port beyond a trusted network** (ADR-008 items 1-3), regardless of what the toolset roster can do. This was a conscious, reviewed decision (not a silent policy drift) — recorded here specifically so a future reader doesn't find write tools shipping over HTTP and wonder whether ADR-008 was simply forgotten.

## ADR-012 — Voxel viewer listener binds all interfaces; its port is exposed independently of the MCP endpoint (2026-07-25)

*Superseded in part by ADR-016: the "always bind all interfaces" decision. The viewer is now loopback by default and a container opts in to `0.0.0.0`. The independent-exposure reasoning below still stands.*

**Context:** `VoxelViewerBroadcastService` (plan 003, ADR-010) bound its `HttpListener` to `http://127.0.0.1:{port}/voxel/` — correct for the toolset's original direct-on-host reference scenario (stdio, `dotnet run` on the same laptop as the browser), but a real bug once Tool_Box runs inside Docker for LLM_Monitor integration: Docker's `-p hostPort:containerPort` publishing forwards traffic addressed to the *container's* real interface, and a socket bound only to loopback never receives that traffic at all — no `ports:` configuration on any consuming compose could have worked around this, because the listener itself was never reachable from outside its own container's network namespace. Found while wiring up the viewer through LLM_Monitor's compose, where the tool calls themselves were already confirmed working over the MCP endpoint, but the browser viewer had never worked through any Docker path — not a regression, a gap present since plan 003 shipped.

**Decision:** Two changes, kept conceptually separate: (1) the listener now binds `http://+:{port}/voxel/` (HttpListener's strong wildcard — all interfaces), the same class of fix `ToolBoxHttpApp.cs` already needed for the MCP endpoint (`ASPNETCORE_URLS=http://0.0.0.0:8080`), just expressed in `HttpListener`'s own prefix syntax rather than Kestrel's; `+` still accepts loopback connections, so the direct-on-host scenario is unaffected. (2) Publishing the viewer's port (8090) is treated as its own, separate exposure decision from the MCP endpoint's (still unpublished per ADR-008/011) — because the viewer channel is receive-only and human-eyes-only by construction (`VoxelViewerBroadcastService`'s own doc comment: "the agent never talks to this"), exposing it carries none of the tool-execution risk ADR-008's lockdown posture is actually guarding against. Tool_Box's own dev compose and LLM_Monitor's consuming compose both now publish `8090:8090` explicitly, while the MCP port (8080) stays unpublished in the consuming compose exactly as before.

**Consequences:** Requires a new image publish before the fix takes effect anywhere it's consumed as a pinned tag (LLM_Monitor's compose currently pins `ghcr.io/timothy-lee-grant/tool_box:1.0.1`, built before this fix — the `ports:` entry added there is inert until a newer tag is pinned). `docs/TOOL_CATALOG.md`'s Voxel notes and `docker-compose.yml` both updated to stop asserting `127.0.0.1` as the bind address while still being accurate that `127.0.0.1`/`localhost` is exactly what a *host machine* browser should point at once the port is published. Establishes a reusable precedent: a toolset's companion infrastructure (ADR-010) can have its own exposure posture, decided independently of the MCP transport's, provided the reasoning (what capability does this channel actually grant a caller?) is written down here rather than assumed by analogy.

## ADR-013 — Issue-driven AI workflow: the GitHub issue is the task's memory (2026-11-06)

**Context:** Development so far used long, staged implementation-plan documents, plus a `CLAUDE.md` that held every convention. Every agent session loaded all of it regardless of the task, so context grew with the project rather than with the task. The next phase (v2: GUI control center + RAG, plus consolidating old branches) is larger than any plan so far, and `main` must stay stable because it is linked from Timothy's résumé.
**Decision:** Work is tracked as GitHub issues and executed by Claude through `anthropics/claude-code-action` (`.github/workflows/claude.yml`), triggered by `@claude` mentions or the `claude` label. Memory is layered: `CLAUDE.md` holds only global facts and rules; the issue thread (body + comments, with an end-of-session `## Session notes` comment) holds task state; ADRs hold durable decisions; documentation conventions moved to `Documentation/CONVENTIONS.md`. The existing five-stage process is kept as `stage-*` labels. Specialist subagents (`planner`, `reviewer`, `lecturer`) run in fresh contexts. Verification is delegated to CI. All agent PRs target a new `next` integration branch; `main` changes only by an explicitly reviewed merge.
**Consequences:** Session context is bounded by the issue rather than by the project. The workflow file must live on the default branch (`main`) for issue events to fire, so this one docs-and-config change is merged to `main`; every later change goes through `next`. Agent runs consume the Claude subscription's usage (or API credit, if switched to a key), and Actions minutes are free for this public repo. The queue runner (`claude-queue.yml`) is manual-only until the interactive mode has proved itself. Plans 001–005 remain as the historic record.

## ADR-014 — v1 is archived as tag `v1.0.2` plus a GitHub Release, not a folder; v2 evolves in place (2026-11-07)

**Context:** Before the v2 work (GUI control center, RAG, Embedded toolset), v1 — a simple MCP server with the Basics and Voxel toolsets, plus its lectures, plans and ADRs — needed to stay permanently findable as a reference and study record. Three options were compared in issue #10: (1) a tag plus GitHub Release, (2) an `OlderImplementation/` folder, (3) keep v1 in place with no archive. Issue #11 separately decided that v2 evolves the existing Host/Core/Toolset code through a toolset-catalog seam rather than being rewritten.
**Decision:** Archive v1 as the **existing annotated tag `v1.0.2`** (the merge of PR #4, "Fixing Issues With Voxel World Viewer") with a GitHub Release carrying notes: what v1 is, links to its lectures, plans and ADRs, and `git checkout v1.0.2`. No new tag is created and there is no `archive/v1` branch. `v1.0.0` and `v1.0.1` stay untouched. No code is copied into a folder. `Documentation/` stays in place and intact, and `README.md` gains a "v1 archive" section pointing at the release.
**Consequences:** A tag is an immutable pointer, so there is no second copy of the code to build, test, or drift. CI and the Dockerfile are unaffected (`ci.yml` builds only what it checks out). Reusing an existing tag avoids re-triggering `docker_image_release.yml` (which fires on `v*.*.*`); Timothy confirmed a Docker publish would have been acceptable, but it is not needed. Cost: browsing v1 code means opening the tag on GitHub or checking it out, rather than seeing a folder. Lectures written after the tag exist only in the working tree, which is why `Documentation/` must never be moved.

## ADR-015 — Toolsets are composed from a catalog plus configuration; disabled toolsets are never registered (2026-11-08)

*Superseded in part by ADR-018: the "disabled toolsets are never registered" rule. Every toolset is now registered and the reconciler gates what is started and visible. The catalog, the config layering and the fail-loud rule for unknown ids still stand.*

**Context:** `ToolBoxServerComposition` hard-coded `.AddBasicsToolset().AddVoxelToolset()`, so the roster was fixed at compile time. The v2 GUI (S1/S2) needs to toggle toolsets, and the Embedded toolset must exist without being on by default. ADR-003 forbids Core from referencing any toolset, and Core must stay free of the MCP package.
**Decision:** Core defines `ToolsetCatalogEntry(Id, Name, Description, Action<IServiceCollection> Register)` and `ToolsetCatalog` (rejects blank/duplicate ids, case-insensitive; `Compose` throws on an unknown id and lists the valid ones). Each toolset exposes one `CatalogEntry` beside its `Add<Name>Toolset()` doorway; the doorway is refined, not superseded (ADR-005 still holds). The Host's `ToolBoxCatalog` is the only list of entries. `Register` takes `IServiceCollection` rather than `IMcpServerBuilder`, which keeps Core MCP-free; each entry calls `AddMcpServer()` (proved idempotent by test). The enabled set resolves, last wins: code default (`basics`, `voxel`) < appsettings `Toolsets:Enabled` < `TOOLBOX_TOOLSETS` (comma-separated, its own key so arrays don't merge by index) < in-memory overrides. An explicitly empty `TOOLBOX_TOOLSETS` enables nothing. Only enabled entries' `Register` runs, so a disabled toolset's tools, descriptor and hosted services (ADR-010) never exist. The Host logs the enabled toolsets on stderr at startup (ADR-004). The release version moves to 1.1.0, set once in `Directory.Build.props`.
**Consequences:** Default behaviour is unchanged (Basics + Voxel). Registering everything and filtering at runtime was rejected: more code, and Embedded's firmware lookup would still run. A bad id fails startup loudly. Changing toolsets still needs a restart; live switching and any control API are S1+. Adding a toolset is one project reference plus one line in `ToolBoxCatalog.Create`. `/health` now reports `1.1.0.0`.

## ADR-016 — Bind address is configuration, loopback by default; port conflicts fail fast (the viewer degrades visibly) (2026-11-08)

**Context:** Ports and bind addresses were scattered: Kestrel defaulted to `localhost:8080`, the viewer hard-coded `http://+:8090..8093/` (ADR-012: all interfaces, so Docker publishing works) with a silent fallback to the next port, and a taken MCP port surfaced as a raw Kestrel exception that named no service. A laptop run therefore exposed the viewer on every interface, and a background host could fail mysteriously. Issue #37 (epic #23, decision 10) asked for one port table, conflict detection and loopback in desktop mode.
**Decision:**
- **One table.** `PortTable` in the Host holds the defaults: MCP 8080, Admin 8095, Viewer 8090, all on `127.0.0.1`. It is seeded as the lowest configuration layer (HTTP and stdio), and Voxel reads its own `Ports:Viewer:*` keys from it. Keys are nested: `Ports:<Service>:Port` and `Ports:<Service>:Address`, overridable with `TOOLBOX_Ports__<Service>__Port` and `__Address`. Precedence is in `docs/ARCHITECTURE.md` §4. `ASPNETCORE_URLS` and `--urls` still win for MCP, with a warning if `Ports:Mcp:*` is also set. Port `0` means "OS picks" and skips the probe.
- **Bind address is configuration.** Loopback is the default. Containers set `0.0.0.0` explicitly in the `Dockerfile` and `docker-compose.yml` (`TOOLBOX_Ports__Mcp__Address`, `TOOLBOX_Ports__Viewer__Address`); the Dockerfile no longer sets `ASPNETCORE_URLS`. This supersedes only the "always bind all interfaces" part of ADR-012. The admin address must be loopback: any other value refuses to start. The viewer in loopback mode registers two `HttpListener` prefixes (`127.0.0.1` and `localhost`), because `HttpListener` matches the request `Host` header and `viewer/index.html` connects to `localhost`.
- **Conflict detection (D2 + thin D1).** A pre-flight `TcpListener` probe on the same address as the real bind reports a conflict by service, port, address and config key. The real bind failure is also translated into the same `PortConflictException`, which covers the race between probe and bind.
- **Required vs optional.** MCP is required, so a conflict stops the host with exit code **3**. The viewer is optional: a conflict never crashes the host; it sets `components.viewer` to `unavailable: port N in use`, logs a warning, and MCP keeps working. The 8091–8093 fallback is removed: one fixed port is what the browser page and the compose mapping both assume. Automatic reassignment stays out of scope.
- **Health.** `/health` adds `components` from a Core `ComponentStatusRegistry`. `status` is `"ok"` when every enabled component is healthy and `"degraded"` when an optional one is down, both with HTTP 200 so the container healthcheck keeps passing. The admin API (#35) and the GUI (S2) read the same snapshot.
- **Exit codes** are part of the host's contract: **2** = unknown transport, **3** = a required port is already in use.
**Consequences:** Desktop runs are private to the machine by default. The default MCP bind moves from `localhost` to `127.0.0.1`, which is IPv4 only, so a client that resolves `localhost` to `::1` will not connect (rare; set `Ports:Mcp:Address` to override). Images that still set `ASPNETCORE_URLS` keep working, because it takes precedence by design. A container needs the two bind-address variables or its published ports reach nothing. The stdio transport has no `/health`, so a degraded viewer there only appears as a stderr warning until the admin API exists. A probe cannot be perfect, so the bind-failure translation remains the backstop. The admin port is validated and listed now; #35 adds its listener and probe.

## ADR-017 — Desired-state file: user intent layered between appsettings and the env-var pin (2026-11-09)

**Context:** The GUI and background host (epic #23) need to persist what the user *wants* (which toolsets are on, per-toolset settings) separately from what is running. `TOOLBOX_TOOLSETS` and `Toolsets:Enabled` (ADR-015) are deployment config, a different question from user intent. Decision 7 of the epic says agents cannot change settings, so only the GUI and admin API write.
**Decision:**
- **Layering.** The file is a new layer between `appsettings.json` and `TOOLBOX_TOOLSETS`. Resolution yields *desired* (code default < appsettings < file) and *effective* (after the env-var pin and test overrides), plus `pinnedBy`. When `TOOLBOX_TOOLSETS` is set it is authoritative for `enabled` on every known id (named on, unnamed off), because today's Docker and CI behaviour must not change; file *settings* are still honoured. No file means exactly the pre-file behaviour. Rejected: the file replacing env/appsettings in a mode (two code paths, silently ignored env vars) and the env var seeding the file (write-once magic, makes the host a writer).
- **Location.** `Environment.SpecialFolder.LocalApplicationData/ToolBox/desired-state.json` (per-machine, no roaming, no platform branching; native `~/Library/Application Support` on macOS with .NET 8+). Override with `Desired:Path` / `TOOLBOX_Desired__Path`. Docker skips the file by default; a volume plus the path variable is the opt-in.
- **Format.** JSON, a map keyed by toolset id, `enabled` optional (absent = no opinion), `settings` an opaque `Dictionary<string, JsonElement>` so Core stays toolset-agnostic (ADR-003). Unknown fields round-trip via `[JsonExtensionData]`. Integer `schemaVersion` with a sequential migration table (empty at v1).
- **Store.** `Load()` never throws and never writes, returning Missing/Ok/Corrupt/Unsupported. `Save()` takes a process-wide lock, re-checks the file, writes a temp file in the same directory, flushes, and renames over the target (`0600` on Unix). A corrupt file is copied to `desired-state.json.bad-<UTC>` only at the next save. A newer `schemaVersion` is refused and left byte-identical.
- **Failure policy.** Fail soft: a corrupt or unsupported file falls back to defaults, logs one stderr line and reports `components.desiredState` in `/health` (`degraded`, HTTP 200). A missing file reports nothing. Unknown ids in the file are preserved and ignored with a warning; unknown ids in the env var or appsettings still fail startup, since those are operator errors.

**Consequences:** The roster is still read once at startup; the reconciler (#32) will compare desired and effective, and the admin API (#35) is the only caller of `Save`. Cross-process write safety relies on that single writer. Hand-editing is allowed but unsupported. Per-toolset setting validation is deferred until a toolset defines real settings. A file watcher is deferred to #32.

## ADR-018 — Registration is cheap and side-effect-free; startup is what's gated (2026-11-09)

*Supersedes ADR-015 in part: its "disabled toolsets are never registered" rule. ADR-015 was scoped to startup-only composition (S0), where the roster was fixed at `Build()`. Its catalog, its config layering and its fail-loud rule for unknown ids still stand.*

**Context:** The S1 reconciler (#32) must turn toolsets on and off while the process runs, but the DI container freezes at `Build()`, so a toolset that was never registered can never be switched on. Options compared on the issue: (A) rebuild the inner server, (B) register everything and gate at runtime, (C) one host per toolset. B was chosen: A loses Voxel's world and has no answer for the stdio session, and C is a process supervisor plus an aggregating proxy (out of scope).
**Decision:**
- `ToolsetCatalog.ComposeAll` registers every toolset. Registration must be cheap and side-effect-free: no port binding, no filesystem walk, no background work. Embedded's firmware lookup is a lazy factory resolved in `EmbeddedLifecycle.Start`.
- Side effects live behind Core's `IToolsetLifecycle` (`Start`/`Stop`). `ComposeAll` rejects any toolset that registers a raw `IHostedService`, because the container starts those at boot and nothing can stop them. The Voxel viewer is a restartable singleton driven by `VoxelLifecycle`.
- `ToolsetReconciler` (Core, pure logic, injected `TimeProvider`) diffs desired against actual, starts a toolset then opens the `ToolsetGate`, and closes the gate then stops. A failing toolset is marked `Failed` with a reason and the others carry on. A failed toolset is retried on the next desired change or manual request, with no timed retry. `ToolsetReconcilerService` (Host hosted service) reconciles to `EnabledResolution.Effective` at startup and to nothing at shutdown.
- One choke point: `ToolsetGateFilters` (MCP list and call filters) and `ServerInfoProvider` ask the gate. A closed toolset's tools are hidden from `tools/list`, and a call returns the error `toolset 'x' is off`, not "tool not found". The gate's `Open`/`Close` are internal to Core, `Host` and its tests, so only the reconciler writes it.
- Unknown ids from env or appsettings still fail startup, listing the valid ids (`ValidateIds`).
- Turning Voxel off keeps its `VoxelWorld` in memory; only an explicit reset clears it. S3 adds disk persistence. An occupied viewer port keeps Voxel On with `components.viewer` unavailable (ADR-016).

**Consequences:** Every toolset's tools exist in the container even when off, so every future toolset must follow the "cheap to register" rule; the hosted-service check enforces the most likely violation. HTTP mode is stateless (ADR-007), so changes reach clients on their next `tools/list` or session, and push notifications are #34's concern. File-watch and manual triggers come in a later step of #32.

**Addendum (2026-11-09, review of #32):** The gate fails open for a tool with no owning toolset, because failing closed would hide legitimate tools from every client if the owner map were ever wrong. The guard is a test that every registered `McpServerTool` has an owner, so a violation fails CI instead. The gate covers tools only: resources and prompts would bypass it, and no toolset registers any today. Any future toolset that adds resources or prompts must extend the gate first. `IToolsetLifecycle` also documents that `StartAsync` must leave nothing running if it throws, and `StopAsync` is never called after a failed start.

## ADR-019 — Admin API: a second loopback listener, separated by socket port, guarded by a bearer token (2026-11-10)

**Context:** The GUI (S2) and curl need to read and change toolset state, while agents must not (epic #23, decision 7). Issues #35 (API) and #36 (token) were planned together and ship as two PRs, auth first, so the API never exists on `next` unauthenticated.
**Decision:**
- **Control plane vs data plane.** MCP is the data plane. The admin API is plain minimal-API routes under `/api/v1`, never MCP tools, on its own loopback listener (`Ports:Admin`, 8095) added to the same `WebApplication` as a second URL (admin appended last). A second `WebApplication` and a hosted service owning its own Kestrel were rejected as more ceremony than a loopback API needs.
- **Socket-port separation.** `PlaneSeparationMiddleware` runs first and decides by `HttpContext.Connection.LocalPort`, recorded by `AdminListener` after start (port 0 in tests). `/api/v1` is 404 on the MCP port; everything else is 404 on the admin port. The `Host` header is client-controlled, so `RequireHost` is not a boundary; a test sends a forged `Host` to the MCP port.
- **Token auth.** 32 random bytes, base64url, in a file next to the desired-state file (0600 file, 0700 directory on Unix; Windows relies on the per-user LocalApplicationData ACL). Created at startup with a temp file plus move-without-overwrite so a lost race keeps the winner's token. Sent only as `Authorization: Bearer`; never in a query string, log, response or exception. Compared as SHA-256 hashes with `FixedTimeEquals`. Core owns `AdminTokenStore` so the GUI reads the same file as the same OS user; no endpoint hands the token out.
- **Rotation.** Replacing the file works with no restart (the token is re-read when mtime or length changes), and `POST /api/v1/token/rotate` returns 204 with no body. A CLI is deferred.
- **Rebinding defences.** One guard middleware on the admin socket, before routing and before auth: Host allowlist (loopback names plus the real port, else 421), Origin check (present and not loopback on the admin port, else 403), no CORS headers at all, JSON content type required on writes (415). Because it guards the socket rather than individual routes, a new endpoint cannot bypass it; a test enumerates `/api/v1` endpoints and asserts 401 without a token. Bearer auth is the real barrier; Host/Origin are defence in depth.
- **Startup.** HTTP mode only. The admin port gets the same preflight as MCP (exit 3, naming `Ports:Admin:Port`). **stdio opens no admin listener in v1**: several stdio hosts can run at once and would fight over the port; they still follow the file via the watcher. `Admin:Enabled` is the future switch (it would move the listener into a hosted service and need its own ADR). In Docker the token lives under `/tmp/toolbox` because the non-root user cannot write `/app`.

**Consequences:** The admin port is a required port, so a conflict stops the host. The admin URL being the last entry of `app.Urls` is an assumption pinned by tests; Kestrel options are the fallback. Tests run on real Kestrel through `HttpServerFixture`, since `TestServer` has no socket and cannot test port separation. A test `ModuleInitializer` redirects the token path so tests never touch the real home directory. The MCP port has the same DNS-rebinding exposure and is tracked separately in #66. Toolset endpoints and their write semantics get their own ADR in PR 2.
